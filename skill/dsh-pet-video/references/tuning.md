# 调参：往哪个方向拧

原则：**先跑默认值，再 QA，再按症状调。** 不要一上来就调参数——
你还没有一个客观标准判断调好没有，盲目调只会把问题挪到别的地方。

---

## 契约参数（不是调优项，是必须对齐的）

这两个值定错了不会报错，但结果会整体错位，**先确认它们再谈调优**。

| 参数 | 规则 |
|---|---|
| `seg_frames.py --fps` | 必须与 `forge video --fps` **完全一致**。`--frames-dir` 模式下，forge 按 `t = 帧序号 / fps` 反推每帧的时间，两处不一致 → `--segments` 里的秒数全部错位 |
| `forge video --frames 8` | 每个动作取几帧。图集一行 8 格，**8 是上限**。实际回放帧率 = `帧数 ÷ 片段时长`，所以 1.0 秒片段取 8 帧 ≈ 8fps，接近原速 |

顺带推一下片段长度：`片段时长 ≈ 帧数 ÷ 想要的回放帧率`。
想按原速回放 12fps 的素材、又只能取 8 帧 → 片段就该是 8/12 ≈ 0.67 秒。
片段拉到 1.2 秒还取 8 帧，就是在 1.8 倍速播放，看起来会"急"。

## 抠像参数（`seg_frames.py`）

| 参数 | 默认 | 它到底控制什么 |
|---|---|---|
| `--ramp-lo` / `--ramp-hi` | 0.40 / 0.70 | 把"人"的概率图映射成 alpha 的斜坡区间。概率低于 lo → 全透明，高于 hi → 全不透明，中间线性过渡。**这是最该调的旋钮** |
| `--dilate` | 1 | 只在"最大连通域附近"保留像素，用来丢掉画面里零星误检的小块。调大更容易删掉误检，但也可能切掉细小的肢体 |
| `--feather` | 0.8 | 边缘高斯羽化 sigma。调大边缘更柔（缩放后锯齿更少），但太大会让人看起来"糊" |
| `--model` | mobilenet | `resnet50` 边缘明显更准，CPU 上慢好几倍。只在 mobilenet 明显不够用时换 |
| `--flatten` | none | 把结果合成到纯色底（`white` / `green`）而不是透明。**配合 forge 原生色键用**，见下面最后一行 |

### 按症状调

| 症状 | 往哪拧 | 为什么 |
|---|---|---|
| 人周围有一圈**背景色的脏边**（合成到桌面上一眼可见） | `--ramp-lo 0.45`（收紧） | 软 alpha 的半透明边缘里混着原始背景色，阴影渲染出来就是一圈脏色。收紧斜坡让 matte 往里缩一点，用掉最外侧那圈混合像素 |
| 边缘**明显锯齿**，缩到 224px 后更明显 | `--feather 1.2`～`1.5` | 羽化把硬边摊开。注意别过头，过 1.5 会开始发虚 |
| **手臂/腿被切掉**，或细长部位断裂 | `--ramp-lo 0.35`（放宽）、`--dilate 0` | 细肢体的"人"概率本来就低，斜坡下沿太高会把它们判成背景 |
| 画面里**留着一个小色块**（误检） | 先确认 `--dilate ≥ 1`（默认就是 1） | `--dilate` 的作用是"只保留最大连通域附近 N 像素内的 alpha"。远处的孤立误检**已经被最大连通域这一步丢掉了**；但如果你把它设成 `0`，这个限制会整个失效，反而会放进更多误检。所以别往小了调 |
| 主体边缘被削得**比实际瘦一圈** | `--dilate 2` | 保留范围往外扩，把软边重新纳入 |
| **主体被抠成碎片** | 检查是不是素材里主体太小 | 面积中位数 < 0.08 基本没救，换素材或换路线 |
| 面积突然翻倍、边缘出现**大块背景** | 见 `pitfalls.md` 第 5 号坑 | 泛洪补洞吃掉了背景。`seg_frames.py` 已修，自己写脚本时记得补边 |
| 深色衣服/头发边缘被吃掉 | `--ramp-lo 0.35`、`--feather 1.0` | 深色区域概率偏低 |
| 调了半天边缘还是不满意 | 试 `--flatten white` + forge 原生色键（`--key white`） | 换成"人贴在纯白底上，再让 forge 自己抠白"。forge 的连通域泛洪**不会吃掉角色内部的白色**（白眼球、白衣服是安全的），而且它的 `despill` 处理边缘比我们手写的干净。这是被低估的兜底方案 |

> 判断"边缘脏不脏"的可靠办法：把 RGBA 帧合成到一个**深色**背景上看（比如深灰）。
> 白底上看不见的脏边，深色底上一览无余——桌宠实际就活在透明/深色底上。

## 分段参数（`plan_segments.py`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `--window` | 1.0 | 每个动作片段的时长（秒）。按上一节的公式算：`window ≈ frames / 目标fps` |
| `--step` | 0.25 | 候选窗口的滑动步长。调小只会让候选更密，不改变分配逻辑 |

分配逻辑的优先级和理由写在 `SKILL.md` 第 4 步的表里。
要改分配（比如用户只要 3 个动作、或者要额外加 `waving`），
直接编辑脚本里的 `picks` 列表——它就是一个 `(动作, 排序键, 取最大?, 理由, 额外筛选)` 的数组，
加一行就能多分配一个动作，互不重叠的约束由 `overlaps()` 自动保证。

### 什么时候 `trend`（主体增长趋势）这个信号不可靠

它用"主体占幅随时间的线性斜率"来猜"是不是朝镜头冲过来"。缺点：

- **噪声敏感**：最平静的片段稍微涨一点点就会拿到最大 trend。所以脚本加了
  `motion >= 中位运动量` 的筛选，确保 `jumping` 同时是个"有动作"的时刻
- **分不清"走近"和"站起来"**：两者都让占幅变大
- **镜头在动就完全不成立**：固定机位的假设不满足时，trend 没有意义

所以 `jumping` 的自动结果**最值得人工复核**。短视频尤其如此——
素材里可能根本没有"跳"这个动作，那就老老实实把某个活跃片段给 `jumping`，
并在交付时说明"这是抽象映射，不是真的在跳"。

## 色键路线的参数（`verdict = chroma-ok` 时）

这几个是 `dsh-pet-forge` 自带 video 命令的参数，调不动时按顺序试：

| 顺序 | 参数 | 作用 |
|---|---|---|
| 1 | `--similarity 0.22` | 相似度阈值。抠不干净先动它 |
| 2 | `--erode 1` | alpha 腐蚀，收掉残留的一圈幕布边 |
| 3 | `--spill 0.9` | 去幕布反光（绿边、蓝边） |
| — | `--key 0x00FF00` | 自动取色不对时手填幕布色 |

还是不行 → 让用户换更均匀的幕布重拍。
**别在 `scene` 素材上浪费时间调这些**，那是路线选错了，不是参数没调好。

## 音频参数（`extract_video_audio.py`）

| 参数 | 默认 | 往哪拧 |
|---|---|---|
| `--fade-ms` | 30 | 截断处有"啪"的爆音就调大（50~80）。连续音乐被硬切一刀必然有边界噪声，这个是最便宜的修法 |
| `--target-rms-db` | -20 | 整体偏吵调到 -23 ~ -26；偏轻调到 -17。**注意它是"目标"，不是"上限"** —— 小声的片段会被**提升**到这个值，这正是第 14 号坑的来源 |
| `--click-sec` | 0.35 | 点击感不够脆就缩短到 0.2；想要更明显的反馈拉到 0.5 |
| `--dive-sec` | 0.7 | 连点三次的反馈，一般比 click 长一倍比较自然 |
| `--rate` | 44100 | 桌宠音频没必要更高。降到 22050 能把文件减半，听感差别很小 |
| `--map` | 动作段同名映射 | 换映射不用改代码，例：`--map "boot=review,celebrate=jumping"` |

### 响度对齐该用 RMS 还是峰值

用 **RMS**（脚本默认）。纯峰值归一化的问题是：某段只要有一个尖峰，
整段就被压得很轻，几段之间的听感会差很远。RMS 更接近"音量一致"的直觉。
但 RMS 会**放大**小声片段，所以必须配合第 14 号坑那个相对平坦度体检。

### 验收为什么不能只靠 `verify`

`verify` 检查的是"文件在不在、格式对不对"，**它不会播放任何东西**。
一个 0 字节的、或者全静音的 WAV 同样能通过 verify。
唯一能证明"真的有声音"的是让宿主播一次：

```powershell
node <forge> play --id <id> --key celebrate
```

## 值得记住的经验值

**画面**

- 边缘颜色标准差 **< 12** 是幕布，**> 40** 一定是现场背景，中间地带要靠眼睛
- alpha 覆盖率中位数落在 **0.2 – 0.5** 属于正常（人形大约占画面 1/4 到一半）
- 覆盖率 > 0.6 先怀疑泛洪坑；< 0.08 先怀疑主体太小
- CPU 上 DeepLabV3-mobilenet 约 **0.5–1.5 秒/帧**（分辨率越高越慢），
  101 帧大约 1 分钟。`resnet50` 是这个的数倍，先算一下时间再决定要不要换
- 权重 42MB 只在第一次下载，缓存在 `--torch-home`

**音频**

- 频谱平坦度：真实乐音/人声约 **1e-5 ~ 1e-4**，底噪约 **0.1 ~ 1**。
  跨了四个数量级，所以**只做相对比较，别用绝对阈值**
- 一段被提升 **超过 12 dB** 就该怀疑它是不是近乎静音（脚本以此为报警门槛）
- 素材只有 8 秒时，几个音效的取音区间重叠是必然的，不必强行岔开；
  重要的是每个听起来像个独立的小反馈
- 源常见的 48kHz 会重采样到 44.1kHz，别以为解码错了
